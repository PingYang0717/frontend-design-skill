# 如何分析 prototype

產出物是新專案的 `docs/_bootstrap/prototype-analysis.md`(格式見 `templates/prototype-analysis.md`)。
目標不是重現 prototype 的程式碼,而是把它轉成「人和 agent 都看得懂的需求」。

## 原則

1. **prototype 是需求素材,不是要搬進專案的程式碼。** 不複製它的 inline style、假資料結構或元件寫法。
2. **能查證的就查證,不要估計。** 色碼、字級、間距從原始碼或設計檔讀出實際值;讀不到就列入待確認。
3. **不確定就問。** 寫進「待確認問題」,附 2–3 個選項與建議,一次問完。
4. **用使用者看得到的詞命名。** 畫面標題、選單、欄位名稱就是領域名詞的來源。

## 依 prototype 型態讀取

| 型態                               | 怎麼讀                                                                                                                                                                                                                  |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 單一 HTML(打包的 React / Vue 成品) | 先找 `:root` / `[data-theme]` 的 CSS 變數與 `<style>`;再找畫面切換的狀態(常見是一個 view / page 的 state 與 switch)列出所有畫面;找假資料陣列推回資料欄位;找圖示名稱(常見 `ant-design:xxx-outlined` 之類的 Iconify 名稱) |
| 多頁 HTML / 靜態網站               | 每個 HTML 檔是一個候選畫面;共用的 header / 側欄是版面                                                                                                                                                                   |
| Figma 或設計檔連結                 | 讀頁面與 frame 名稱當畫面清單;讀 local styles / variables 當 token;拿不到存取權就請使用者匯出或截圖                                                                                                                     |
| 截圖 / PDF                         | 逐張描述畫面;色碼無法精確取得時,列入待確認並請 UX 提供                                                                                                                                                                  |

大檔案(上萬行)不要整份讀進來:先用搜尋找 `:root`、`theme`、`color`、`fontFamily`、路由或 view 名稱、
`aria-label`、表格欄位定義,再讀相關片段。

## 逐項擷取

### 畫面與路由

- 每個可獨立到達的畫面 → 一個路由;對話框、抽屜、分頁籤屬於所在的畫面,不給路由(除非需要直接連結)
- 原型若用 state 切換畫面(重新整理會回首頁),改用真實路由是**刻意的偏離**,寫在分析的決定紀錄
- 路徑用小寫 kebab-case;單一資源的詳細頁用 `/items/:itemId`

### 元件對映

判斷順序:**antd 有對應元件 → 直接用**;同一個視覺樣式出現兩次以上 → `components/common/` 共用元件;
其餘 → `components/<domain>/` 自製。表格、表單、對話框、下拉、分頁、標籤幾乎都有 antd 對應。

### Design token

- 讀 prototype 的色彩宣告,對到 `theme/tokens.ts` 的欄位(primary、bg*、border*、text*…)
- **light 與 dark 各一組,逐值抄**;prototype 只有一組時,dark 欄寫「未提供」
- 主色等 seed token 若 prototype 的深色值看起來就是 antd 推導的結果,照團隊規則兩主題都餵亮色值
- token 表沒有的顏色(狀態徽章、圖表)另列,說明用途,之後決定加進 tokens 還是用 antd 語意色

### 圖示

Iconify 的 `ant-design:menu-fold-outlined` 對應 `@ant-design/icons` 的 `MenuFoldOutlined`(去掉前綴、轉 PascalCase)。
找不到對應的圖示列入待確認,**不要**用 emoji 或文字頂替。

### 資料與 API 草案

- 從表格欄位、詳細頁、表單欄位、假資料推出每個畫面需要的欄位
- 欄位命名:有後端契約就照契約;沒有就提草案(camelCase、列舉值 SCREAMING_CASE),標為「草案」
- 每個寫入動作(新增、修改、刪除、送出)都是一個端點候選

### 角色與權限

看 prototype 有沒有「依身分顯示不同內容」的地方(管理員選單、唯讀畫面、停用的按鈕)。
權限代碼格式 `<資源>:<動作>`。看不出來就列入待確認,先做單一角色。

### 缺漏狀態

逐畫面檢查:載入中、空資料、讀取失敗、寫入失敗、權限不足、長文字、大量資料、RWD。
prototype 沒畫的,填團隊的預設做法(見輸出範本第 9 節),讓 UX 只需確認例外。

## 停頓點

分析完成後**一定要停下來**問。問法與 mattpocock 的 `grilling` 相同:

- **分輪**:一輪只問「前提都已確定」的題目(frontier);答案會影響別題的,留到下一輪。通常兩到三輪就清空
- **每題**:編號、標題、一句背景、2–3 個選項、**建議答案**;措辭讓「是」就等於接受建議
- **事實自己查,決策才問**:色碼、圖示名稱、欄位這些從 prototype 讀得到的不問;問的是 prototype 沒說、要人拍板的事
- **結束條件**:frontier 空了、沒有任何默默假設的事

第一輪通常是這四類:

1. 待確認問題(分析檔第 11 節)
2. 缺漏狀態中「預設做法」的清單,請 UX 確認或指出例外
3. 路由模式(history / hash)與部署環境
4. 後端現況(已有 / 開發中 / 未開始)與契約來源

每一輪的答案立刻記進分析檔第 11、12 節,名詞決定直接進 `GLOSSARY.md` 草稿,不累積到最後。

使用者不在場(排程或無人值守)時:有建議答案的題目採用建議,在分析檔標記「採用建議(暫定)」;
沒有建議答案的(認證方式、聯絡窗口、環境網址)寫「待確認」。兩者都照常繼續,並列在最後的回報。
